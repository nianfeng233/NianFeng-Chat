# AI 聊天程序架构设计文档

**版本：1.0（定稿）**
**定位：以聊天交互为主的 AI 角色聊天程序，不参与重度 Agent 任务。**

---

## 1. 总体目标

本程序围绕“角色—渠道—消息”构建，核心目标：

- 让模型通过工具发送聊天消息和资料，避免长文本污染聊天上下文。
- 通过工作记忆与渠道记忆分层，实现跨渠道连续性与渠道隔离。
- 通过后端权限系统，防止跨渠道隐私泄露和恶意提示注入。
- 支持私聊、群聊、隐私渠道、Nova 渠道等多种会话形态。
- 保持工具调用流程简单、合法、可审计。

---

## 2. 核心概念

| 概念 | 说明 |
|---|---|
| 角色 | AI 人格实体，拥有全局工作记忆、权限配置、聊天记录库。 |
| 渠道 | 精确到平台内某一会话，如 `qq:private:123456`、`qq:group:789`、`wechat:private:abc`、`nova:web:xxx`。 |
| 消息 | 聊天记录最小单位，带完整元数据。 |
| 轮 | 一次完整调用：一条用户触发消息 + 模型完整答复（含工具调用、多次发送、资料发送等）。 |
| 工作记忆 | 角色级全局短期记忆，仅包含普通私聊消息，不含群聊与隐私渠道。 |
| 渠道记忆 | 当前渠道最近消息，用于保证当前渠道连续性。 |
| 隐私渠道 | 独立工作记忆，默认禁止跨渠道读写。 |
| 群聊渠道 | 不参与工作记忆，仅维护本群最近消息。 |

---

## 3. 存储层设计

### 3.1 聊天记录库

- 按渠道独立维护。
- 存储原始消息，不做摘要。
- 每条消息带稳定 `message_id`、单调 `seq`、`timestamp`、`channel_id`、`sender_id`、`sender_name`、`role`、`content_type`、`content`、`visibility`、`source` 等字段。
- 资料类消息只存引用 `doc_id` 和缩略，不存全文。

### 3.2 资料库

- 存放长文本、文献、资料原文。
- 聊天记录库只存引用和缩略。
- 构建上下文时按需加载原文，放入合法的 `role=tool` 结果中。

### 3.3 工作记忆池

- 角色级全局短期记忆。
- 仅包含普通私聊消息。
- 不包含群聊消息。
- 不包含隐私渠道消息。
- 按 timestamp 排序，默认保留最近 5 轮，实际按 token 预算动态截断。

### 3.4 渠道记忆

- 当前渠道最近 5 轮消息。
- 与工作记忆合并时，按 `message_id` 去重。
- 合并后按 timestamp 全局排序。

### 3.5 审计日志

- 记录敏感操作、权限判定、跨渠道读写。
- 不写入聊天记录库。
- 用于事后追溯。

### 3.6 向量索引

- 用于语义检索。
- 检索结果必须经过权限过滤。
- 支持按渠道、时间、可见性过滤。

## 4. 消息模型与格式化

### 4.1 消息字段

```json
{
  "message_id": "m_123",
  "seq": 123,
  "channel_id": "qq:private:123456",
  "sender_id": "user_001",
  "sender_name": "nianfeng",
  "role": "user",
  "content_type": "text",
  "content": "你好",
  "timestamp": "2026-09-11T16:32:00+08:00",
  "visibility": "shareable",
  "source": "qq",
  "is_bot": false,
  "mentions_bot": false,
  "reply_to": null
}
```

### 4.2 格式选择

- 优先使用紧凑 JSON，便于转义和解析。
- 若使用 XML，必须对 `<`、`>`、`&` 做实体转义。
- 元数据放外层，用户输入内容单独包裹，标记为不可信。

示例：

```json
{
  "meta": {
    "time": "16:32",
    "user_name": "nianfeng",
    "channel": "qq:private:123456"
  },
  "content": {
    "trust": "untrusted",
    "text": "你好"
  }
}
```

### 4.3 渠道 ID 规范

- `qq:private:<qq号>`
- `qq:group:<群号>`
- `wechat:private:<wxid>`
- `wechat:group:<群id>`
- `nova:web:<会话id>`

## 5. 上下文构建

### 5.1 普通私聊

- 顶层：全局工作记忆。
- 下层：当前渠道记忆。
- 合并去重，按 timestamp 排序。
- 总轮数控制在约 10 轮，按 token 预算动态截断。
- 重叠部分以工作记忆为主，当前渠道记忆只补不重复。

### 5.2 隐私渠道

- 独立工作记忆。
- 默认不参与全局工作记忆。
- 默认禁止跨渠道读写，需用户显式授权。

### 5.3 群聊

- 无“轮”概念，按条计算。
- 取当前群最近 20 条消息。
- 每条消息带发送者信息、是否 @ 角色、是否回复角色。
- 群聊消息绝不进入全局工作记忆池。
- 模型需要更多历史时，主动调用读取工具，且只能读取当前群。

### 5.4 时间元数据

- 每条消息带 `timestamp`。
- 系统元数据中带当前时间、时区、日期。
- 模型自行解析“今晚八点”等模糊时间，填入 `start` / `end` 参数。
- 不需要程序额外做自然语言时间解析。

## 6. 工具设计

### 6.1 消息读取工具 `read_messages`

参数：

- `channel`：默认当前渠道；有权限时可指定其他渠道。
- `query`：关键词搜索。
- `seq`：精确序号。
- `relative`：相对序号范围，如基准 5，+1 到 +5 表示 6-10。
- `limit`：返回条数，默认 10。
- `time_start` / `time_end`：精确或模糊时间段。
- `semantic`：语义检索内容。
- `cursor`：分页游标。

返回：

- 消息列表。
- `total`、`returned`、`next_cursor`。
- 过长时返回 token 超限提示，要求缩小范围。

权限：

- 后端校验当前用户、当前渠道、目标渠道。
- 群聊普通用户只能读当前群。
- 隐私渠道默认禁止被其他渠道读取。

### 6.2 聊天消息发送工具 `chat_send`

参数：

- `channel`：默认当前渠道，后端注入默认值。
- `messages`：消息列表，可多条。
- `end`：`true` 表示发送后结束本轮；`false` 表示发送后继续下一轮工具调用。

行为：

- 前端模拟真人打字延迟，逐条推送。
- 每条消息生成独立 `message_id`。
- 同一轮重复内容后端去重。
- 跨渠道发送需权限校验，并记录审计。

### 6.3 资料发送工具 `send_document`

参数：

- 与 `chat_send` 类似，但用于长文本、资料、文献。
- 带 `title`、`summary`、`content_type`、`doc_id`。

行为：

- 原文存入资料库。
- 聊天记录库只存引用和缩略。
- 构建上下文时，资料原文放入合法的 `role=tool` 结果中，让模型看到内容，但不污染聊天记录。

### 6.4 工具调用历史格式

必须使用合法的 `assistant.tool_calls` + `role=tool` 结构。

示例：

```json
{
  "role": "assistant",
  "content": null,
  "tool_calls": [{
    "id": "call_1",
    "type": "function",
    "function": {
      "name": "chat_send",
      "arguments": "{\"messages\":[\"你也好\"],\"end\":true}"
    }
  }]
}
```

```json
{
  "role": "tool",
  "tool_call_id": "call_1",
  "content": "{\"ok\":true,\"message_ids\":[\"m_2\"],\"sent_at\":\"...\"}"
}
```

### 6.5 工具循环规则

- 每轮统一强制调用工具，但不指定具体工具。
- 后端丢弃模型直接输出的 `assistant.content`，不展示给用户。
- 模型可自由选择先读取、搜索、查资料，再发送。
- 发送工具 `end=true` 终止循环。
- 发送工具 `end=false` 发送后返回工具结果，继续下一轮。
- 最大工具轮次默认 10，可配置。
- 资料加载单次限制 token，超限提示分段读取。

## 7. 权限与鉴权

### 7.1 权限来源

- 使用后端真实用户身份，不使用消息正文中的 `<user_id>`。
- 在给消息打标签时生成权限上下文。
- 工具调用时再次校验权限表。

### 7.2 权限表字段

```
role_id, user_id, source_channel, target_channel,
can_read, can_send, can_cross_read, can_cross_send
```

### 7.3 渠道分组

- **私聊**：默认共享全局工作记忆，可配置是否参与。
- **隐私**：独立工作记忆，默认禁止跨渠道读写。
- **群聊**：不参与工作记忆，仅当前群隔离。
- **Nova 渠道**：WebUI 自带渠道，按普通私聊处理。

### 7.4 普通用户与高权限用户

- 普通用户：锁死当前渠道，模型无法读取或发送到其他渠道。
- 高权限用户：可跨渠道读取和发送，但敏感操作需确认。
- 群聊中高权限用户可让角色回顾其他渠道内容，普通用户注入无效。

### 7.5 敏感操作确认

- 模型尝试敏感操作时，程序发送一条系统确认消息。
- 该消息不进入任何聊天记录库。
- 用户在输入框输入“确认”视为同意；输入其他内容统一视为拒绝。
- 确认后继续原工具调用；拒绝则返回工具错误，模型停止或改方案。
- 审计日志记录操作、用户、时间、结果。
- 确认功能可做成角色级开关，允许用户关闭。

---

## 8. 多渠道与并发

- 每个角色使用 FIFO 串行队列处理消息。
- 同一角色同一时间只处理一轮完整调用。
- 多渠道同时发消息时，按到达顺序排队。
- 一轮处理完成后，按 timestamp 排序写入。
- 用户插话进入队列，本轮完成后处理。
- 可选优化：用户插话与下一轮工具结果一并返回，作为 `role=user` 插入，不塞进 `role=tool`。
- 前端提供“停止生成”按钮，中断当前工具循环。

---

## 9. 群聊设计

- 群聊不参与全局工作记忆。
- 每个群只维护自己的聊天记录库和最近 20 条上下文。
- 静默记录全部消息。
- 触发条件由程序定义，如被 @、被回复、有人叫角色名。
- 触发后模型看到最近 20 条 + 触发消息。
- 刷屏多时，模型可主动调用读取工具往上翻。
- 群聊中模型只能读取当前群，普通用户只能发送到当前群。
- 高权限用户可跨渠道，但需权限校验和确认。

---

## 10. 前端交互

- 模型发送消息时模拟真人打字延迟。
- 多条消息逐条推送。
- 显示“正在输入”状态。
- 用户插话排队，或与下一轮工具结果合并返回。
- 敏感确认通过输入框完成，输入“确认”同意，其他拒绝。
- 提供停止生成按钮。
- 资料消息与聊天消息在界面上区分展示。

---

## 11. 配置项

### 角色级

- 工作记忆容量。
- 当前渠道记忆容量。
- 最大工具轮次。
- 敏感确认开关。
- 跨渠道读写权限。
- token 上限。
- 时间解析相关元数据展示。

### 渠道级

- 渠道分组：私聊 / 群聊 / 隐私。
- 是否参与全局工作记忆。
- 是否允许被其他渠道读取。
- 是否允许跨渠道发送。
- 可见性标记。

---

## 12. 错误处理与边界

- 权限不足统一返回“目标渠道不可用”，避免模型反复尝试。
- 读取结果超 token 时提示缩小范围，并返回部分结果。
- 重复发送内容后端去重。
- 工具循环超过最大轮次强制终止。
- 资料过长时分段加载。
- 群聊刷屏不特殊处理，模型自行翻记录。
- 有权限用户手滑跨渠道发送，依赖提示词约束 + 审计。

---

## 13. 实现优先级

1. **第一阶段**：消息模型、聊天记录库、资料库、工具调用、上下文构建、权限校验。
2. **第二阶段**：群聊、隐私渠道、敏感确认、多渠道串行队列。
3. **第三阶段**：语义检索、审计日志、提示词优化、配置项完善。

---

## 14. 已知取舍

- 串行处理牺牲并发，换取一致性和实现简单。
- 工作记忆不存摘要，直接存原文，依赖 token 预算控制。
- 有权限用户跨渠道手滑无法完全避免，靠提示词和审计兜底。
- 群聊刷屏时角色可当“团宠”，不强行承担实际功能。
- 敏感确认只做简单关键词判断，不做复杂状态机。

---

**结论：**
本方案以工具调用为核心，将聊天消息与资料分离，通过工作记忆与渠道记忆分层、后端权限校验、群聊隔离、敏感确认和串行队列，实现了一个可落地、可扩展、隐私边界清晰的 AI 聊天程序架构。
